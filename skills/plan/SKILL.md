---
name: plan
description: Use when planning a task.
argument-hint: "[--effort low|medium|high]"
---

The goal is to turn the user's intention into a concrete plan they can approve.

After approval, continue through [Iterate](../iterate/iterate/SKILL.md) → [Ship](../ship/ship/SKILL.md) within the approved scope, following the review and handoff steps below.

Follow [Plan recording](references/recording.md), including standalone use. Use the host's plan mode and question interface when available, entering plan mode when the host allows it. Otherwise run the same flow in conversation. Respect the host's active mode.

1. Read the request, existing decisions, and task records. Identify the development targets and task kinds from the request and repository. Combine affected surfaces instead of choosing one exclusive type. State the goal, constraints, success criteria, and unresolved choices. Keep user requirements distinct from proposed implementation choices.
2. Follow [Research](../utils/research/SKILL.md) to resolve facts from the repository and relevant sources. Follow [decision collection](references/decisions.md) to check every common area and adapt detailed questions to the affected surfaces and task kinds. Use [Socratic](../utils/socratic/SKILL.md) for consequential ambiguities and unresolved decisions that require user judgment. Reuse established answers and directly determining repository contracts.
3. Choose effort from task difficulty, or use `--effort`: low needs no independent reviewer, medium needs one, and high uses the [plan debate](references/debate.md).
4. Use [Explain](../utils/explain/SKILL.md) to show a small preview before lengthy preparation or debate. Include a file tree with change-purpose comments for file changes, Mermaid for meaningful structure or sequence, and [code flow](../utils/explain/references/code-flow.md) when behavior needs explanation. Omit inapplicable views. Label unverified proposals.
5. Develop the approach, work units, and adaptation boundaries. Include commit, push, PR creation, and [Moniterate](../ship/moniterate/SKILL.md) through readiness for human review, unless the user limits delivery. Use [Commit](../ship/commit/SKILL.md) and [PR](../ship/pr/SKILL.md) to present the concrete delivery structure before approval.
   - For each commit, show its proposed message, purpose, affected files or behavior, dependencies, and order. Keep supporting tests and documentation with their change and explain how each commit leaves the project working.
   - For each PR, show its included commits, review scope, why it is separate or grouped, target repository, head and base branches, dependency and publishing order, proposed title, and description following the repository template. State ready-for-review or draft status, checks before opening, and Moniterate's completion conditions. Do not assume a single commit or PR.
   - Map success criteria to observable checks and expected results. For behavior changes, trace entrypoints, value flow, packaging, and callers. Resolve consequential choices about proof with the user before dependent preparation.
6. Prepare tests or reproduction within the authorized scope and host mode. When allowed, run them against the unchanged implementation and record the checked files, command or scenario, and result. Distinguish an expected failure from an environment failure. Explain an unavailable or inapplicable baseline. Keep product implementation for Iterate.
7. Present the complete plan, expected result, checks, baseline evidence, and decision ledger. Allow drafts and previews while decisions remain open. Resolve every open item under [decision collection](references/decisions.md) before requesting final plan approval. Record acceptance from existing instructions when they settle the choices. Otherwise, obtain approval of this plan version once. The approval request states the automatic delivery scope, the conditions that stop the run for the user, and, when the host lets the model set a persistent goal, that approval also sets it. Honor explicit approval requests and pending decisions.
8. After acceptance or approval, follow [plan review](references/review.md). Record the current version and reviewer verdicts. Bring blockers to the user immediately and revisit changed decisions without reopening settled choices.
9. After all decisions close and required reviews clear, save the authorized plan in `PLAN.md` and hand off execution. Execution runs in a context that excludes the planning conversation and receives only the task directory and authorized plan. At execution start, when the host lets the model set a persistent goal, set the approved delivery scope and stop conditions as the goal. While host plan mode is still active, return the plan and pending execution instead.
10. In that execution context, proceed to [Iterate](../iterate/iterate/SKILL.md), including standalone Plan use. Pass the task directory, authorized plan, decision evidence, checks, and baseline evidence. A baseline or plan review does not prove implementation success.
11. After Iterate completes, follow [Ship](../ship/ship/SKILL.md) for the approved commit, push, and PR scope. Ship runs Moniterate after publishing the PR. Reuse existing authorization and valid evidence. Relay only decisions that need the user, then continue the same run. Report completion only after Moniterate reports readiness, or record the concrete blocker and next action. Do not infer merge, deployment, or reviewer-message permission.
